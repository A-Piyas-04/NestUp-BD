## 1. PROJECT OVERVIEW

NestUp BD is a comprehensive property rental platform designed specifically for students and professionals in Bangladesh. The application facilitates property listing, searching, booking, and payment processing with a modern web-based interface.

### Technology Stack:
- **Frontend**: React.js with Vite build tool
- **Backend**: Node.js with Express.js framework
- **Database**: MongoDB with Mongoose ODM
- **Authentication**: JWT (JSON Web Tokens)
- **File Upload**: Multer middleware
- **Styling**: CSS with custom variables and responsive design

## 3. BACKEND ARCHITECTURE

### 3.1 Server Entry Point (server/server.js)

**Purpose**: Main application server that initializes the Express app, connects to MongoDB, sets up middleware, and starts the server.

**Key Functionalities**:
- Express server initialization
- MongoDB connection using Mongoose
- CORS configuration for cross-origin requests
- Cookie parser for JWT token handling
- Static file serving for uploads
- Route mounting and error handling
- Server startup on port 3000

**Code Flow**:
1. Load environment variables from .env file
2. Create Express application instance
3. Configure middleware (CORS, JSON parser, cookie parser)
4. Connect to MongoDB database
5. Mount API routes
6. Start server and listen on specified port

### 3.2 Database Models (server/models/)

#### 3.2.1 User Model (User.js)
**Purpose**: Defines the user schema for authentication and profile management.

**Schema Fields**:
- name: String (required, trimmed, min 2 chars)
- email: String (required, unique, lowercase, email validation)
- password: String (required, min 6 chars, hashed)
- role: Enum ['user', 'admin'] (default: 'user')
- isVerified: Boolean (default: true)
- profile: Object containing:
  - phone: String
  - nidNumber: String
  - dateOfBirth: Date
  - gender: Enum ['male', 'female', 'other']
  - occupation: String
  - emergencyContact: Object with name and phone
  - address: Object with street, city, district, postalCode
- preferences: Object for user settings
- createdAt, updatedAt: Timestamps

**Methods**:
- comparePassword(): Compares plain text password with hashed password
- Pre-save middleware: Hashes password before saving

#### 3.2.2 Service Model (Service.js)
**Purpose**: Defines the property/service schema for rental listings.

**Schema Fields**:
- title: String (required, max 200 chars)
- propertyType: Enum ['apartment', 'house', 'room', 'hostel', 'dormitory', 'sublet']
- description: String (required, max 2000 chars)
- location: Object containing:
  - district: String (required)
  - area: String (required)
  - address: String (required)
  - coordinates: Object with latitude and longitude
- price: Number (required, min 0)
- availability: Object containing:
  - from: Date (required)
  - to: Date (required)
  - isAvailable: Boolean (default: true)
- propertyDetails: Object containing:
  - bedrooms: String
  - bathrooms: String
  - squareFeet: Number
  - furnishing: Enum ['unfurnished', 'semi-furnished', 'fully-furnished']
- amenities: Object with boolean flags for various amenities
- images: Array of image URLs
- thumbnail: String (main image URL)
- contact: Object with name, phone, email, whatsapp
- owner: ObjectId reference to User
- rating: Object with average and count
- reviews: Array of review objects
- isVerified: Boolean (default: false)
- isActive: Boolean (default: true)
- createdAt, updatedAt: Timestamps

**Methods**:
- Pre-save middleware: Updates the updatedAt field
- Indexes: Created on location fields and price for efficient querying

#### 3.2.3 Booking Model (Booking.js)
**Purpose**: Manages property booking information and status.

**Schema Fields**:
- service: ObjectId reference to Service (required)
- user: ObjectId reference to User (required)
- startDate: Date (required)
- endDate: Date (required)
- duration: Object with days and months
- basePrice: Number (required)
- totalAmount: Number (required)
- fees: Object containing service fee, cleaning fee, security deposit
- status: Enum ['pending', 'confirmed', 'active', 'completed', 'cancelled', 'rejected']
- paymentStatus: Enum ['pending', 'partial', 'paid', 'refunded', 'failed']
- guestInfo: Object with numberOfGuests and specialRequests
- contactInfo: Object with phone and email (required)
- confirmationCode: String (auto-generated)
- confirmedAt: Date
- createdAt, updatedAt: Timestamps

**Methods**:
- confirm(): Updates status to confirmed and sets confirmedAt
- checkAvailability(): Static method to check date conflicts
- Pre-save middleware: Calculates duration and generates confirmation code
- Virtual property: durationInDays for easy access

#### 3.2.4 Payment Model (Payment.js)
**Purpose**: Handles payment processing and transaction records.

**Schema Fields**:
- booking: ObjectId reference to Booking (required)
- user: ObjectId reference to User (required)
- service: ObjectId reference to Service (required)
- amount: Number (required, min 0)
- currency: String (default: 'BDT')
- paymentMethod: Enum ['mobile_banking', 'bank_transfer', 'credit_card', 'cash']
- paymentDetails: Object containing method-specific details
- status: Enum ['pending', 'processing', 'completed', 'failed', 'refunded', 'cancelled']
- personalInfo: Object with user's personal information
- termsAccepted: Boolean (required)
- processedAt: Date
- failureReason: String
- gatewayResponse: Object for payment gateway data
- refund: Object with refund details
- createdAt, updatedAt: Timestamps

**Methods**:
- markAsCompleted(): Updates status and processedAt
- markAsFailed(): Sets status to failed with reason
- processRefund(): Handles refund processing
- getPaymentStats(): Static method for payment analytics

### 3.3 API Routes (server/routes/)

#### 3.3.1 Authentication Routes (auth.js)
**Purpose**: Handles user authentication, registration, and session management.

**Endpoints**:
- POST /register: User registration with validation
- POST /login: User login with JWT token generation
- POST /logout: User logout with token clearing
- GET /me: Get current user profile (protected)
- PUT /profile: Update user profile (protected)

**Authentication Flow**:
1. User submits credentials
2. Server validates input
3. For login: verify password, generate JWT token
4. For register: hash password, create user, generate token
5. Set HTTP-only cookie with JWT token
6. Return user data (excluding password)

#### 3.3.2 Main API Routes (api.js)
**Purpose**: Core application API endpoints for services, bookings, and payments.

**Service Endpoints**:
- GET /services: Fetch all services with filtering and pagination
- GET /services/:id: Get specific service details
- POST /services: Create new service (protected)
- PUT /services/:id: Update service (protected, owner only)
- DELETE /services/:id: Delete service (protected, owner only)

**Booking Endpoints**:
- POST /bookings: Create new booking (protected)
- GET /bookings: Get user's bookings (protected)
- GET /bookings/:id: Get specific booking (protected)
- PUT /bookings/:id/confirm: Confirm booking (protected)
- PUT /bookings/:id/cancel: Cancel booking (protected)

**Payment Endpoints**:
- POST /payments: Process payment (protected)
- GET /payments/:paymentId: Get payment status (protected)
- GET /my-payments: Get user's payment history (protected)

**Wishlist Endpoints**:
- POST /wishlist/add: Add service to wishlist (protected)
- DELETE /wishlist/remove/:serviceId: Remove from wishlist (protected)
- GET /wishlist: Get user's wishlist (protected)
- GET /wishlist/check/:serviceId: Check if service is in wishlist (protected)

### 3.4 Middleware (server/middleware/)

#### 3.4.1 Authentication Middleware (auth.js)
**Purpose**: Verifies JWT tokens and protects routes.

**Functions**:
- verifyToken(): Extracts and verifies JWT from cookies or headers
- checkAuth(): Ensures user exists and attaches to request object

**Process**:
1. Extract token from cookies or Authorization header
2. Verify token using JWT secret
3. Find user by decoded token ID
4. Attach user object to request
5. Call next middleware or return error

#### 3.4.2 File Upload Middleware (upload.js)
**Purpose**: Handles file uploads using Multer.

**Configuration**:
- Storage: Local disk storage in uploads/ directory
- File naming: Timestamp + original name
- File filtering: Images only (jpg, jpeg, png, gif)
- Size limit: 5MB per file

## 5. DATABASE IMPLEMENTATION

### 5.1 MongoDB Connection

**Location**: server/server.js
**Connection String**: mongodb://localhost:27017/nestup_bd
**ODM**: Mongoose for schema definition and data modeling

**Connection Process**:
1. Load MongoDB URI from environment variables
2. Use mongoose.connect() with connection options
3. Handle connection events (connected, error, disconnected)
4. Implement graceful shutdown on process termination

### 5.2 Database Schema Design

#### 5.2.1 Collections Overview
- **users**: User accounts and profiles
- **services**: Property listings and details
- **bookings**: Booking requests and status
- **payments**: Payment transactions and history

#### 5.2.2 Relationships
- User → Services (One-to-Many): User can own multiple properties
- Service → Bookings (One-to-Many): Property can have multiple bookings
- User → Bookings (One-to-Many): User can make multiple bookings
- Booking → Payment (One-to-One): Each booking has one payment
- User → Payments (One-to-Many): User can have multiple payments

#### 5.2.3 Indexes
- Users: email (unique), createdAt
- Services: location.district, location.area, price, createdAt
- Bookings: user, service, startDate, endDate
- Payments: user, booking, status, createdAt

### 5.3 Data Validation

**Schema-Level Validation**:
- Required fields enforcement
- Data type validation
- Enum value restrictions
- String length limits
- Number range validation
- Email format validation

**Application-Level Validation**:
- Business logic validation
- Cross-field validation
- Custom validation functions
- Error message customization

## 6. API ENDPOINTS AND DATA FLOW

### 6.1 Authentication Flow

**Registration Process**:
1. Frontend: User submits registration form
2. Frontend: POST /api/auth/register with user data
3. Backend: Validate input data
4. Backend: Hash password using bcrypt
5. Backend: Create user in database
6. Backend: Generate JWT token
7. Backend: Set HTTP-only cookie with token
8. Backend: Return user data (excluding password)
9. Frontend: Update AuthContext with user data
10. Frontend: Redirect to dashboard

**Login Process**:
1. Frontend: User submits login form
2. Frontend: POST /api/auth/login with credentials
3. Backend: Find user by email
4. Backend: Compare password with stored hash
5. Backend: Generate JWT token if valid
6. Backend: Set HTTP-only cookie with token
7. Backend: Return user data
8. Frontend: Update AuthContext
9. Frontend: Redirect to intended page

### 6.2 Service Management Flow

**Service Creation**:
1. Frontend: User fills ProvideService form
2. Frontend: Upload images via FormData
3. Frontend: POST /api/services with service data
4. Backend: Validate user authentication
5. Backend: Process uploaded images
6. Backend: Create service in database
7. Backend: Return created service data
8. Frontend: Show success message and redirect

**Service Search**:
1. Frontend: User applies filters on Search page
2. Frontend: GET /api/services with query parameters
3. Backend: Build MongoDB filter object
4. Backend: Execute paginated query with population
5. Backend: Return services array with pagination info
6. Frontend: Transform data for display
7. Frontend: Render ListingCard components

### 6.3 Booking and Payment Flow

**Complete Booking Process**:
1. Frontend: User clicks "Book" on ListingCard
2. Frontend: Navigate to Payment page with property data
3. Frontend: User completes payment form steps
4. Frontend: POST /api/bookings to create booking
5. Backend: Validate service exists and availability
6. Backend: Check for booking conflicts
7. Backend: Calculate total amount and fees
8. Backend: Create booking with 'pending' status
9. Backend: Return booking data with ID
10. Frontend: POST /api/payments with booking ID
11. Backend: Validate payment details
12. Backend: Create payment record
13. Backend: Update booking payment status
14. Backend: Return payment confirmation
15. Frontend: Show success message
16. Frontend: Navigate to dashboard

### 6.4 Wishlist Management

**Add to Wishlist**:
1. Frontend: User clicks "Save" on ListingCard
2. Frontend: POST /api/wishlist/add with serviceId
3. Backend: Validate authentication and service
4. Backend: Check if already in wishlist
5. Backend: Add to user's wishlist array
6. Backend: Return success response
7. Frontend: Update UI state

## 7. AUTHENTICATION SYSTEM

### 7.1 JWT Implementation

**Token Generation**:
- Payload: { userId, email, iat, exp }
- Secret: Stored in environment variables
- Expiration: 7 days
- Storage: HTTP-only cookies for security

**Token Verification**:
- Middleware: verifyToken() function
- Extraction: From cookies or Authorization header
- Validation: JWT signature and expiration
- User Lookup: Find user by decoded ID
- Request Attachment: Add user object to req.user

### 7.2 Password Security

**Hashing**:
- Algorithm: bcrypt with salt rounds (10)
- Timing: Pre-save middleware in User model
- Comparison: comparePassword() method
- Storage: Never store plain text passwords

### 7.3 Route Protection

**Protected Routes**:
- All routes requiring authentication use verifyToken middleware
- Additional checkAuth middleware ensures user exists
- Role-based access control for admin functions
- Owner-only access for service management

### 8.1 Payment Methods

**Supported Methods**:
- Mobile Banking (bKash, Nagad, Rocket)
- Bank Transfer
- Credit/Debit Card
- Cash Payment

**Method-Specific Data**:
- Mobile Banking: Phone number, transaction ID

### 8.2 Payment Processing

- processing: Payment being processed
- completed: Payment successful

**Processing Flow**:
1. Create booking first
2. Validate payment details
3. Create payment record
4. Process payment (simulated)
5. Update payment status
6. Update booking payment status
7. Send confirmation

**Data Tracking**:

- Status change history
- Payment method details
- Associated booking information
- Refund tracking

**Dashboard Integration**:
- Payment history view in dashboard

## 12. MONGODB COLLECTIONS AND SCHEMA

### 12.1 Collection Initialization

**Location**: Models are defined in server/models/ directory
**Initialization**: Mongoose automatically creates collections when first document is inserted
**Connection**: Established in server/server.js using mongoose.connect()

### 12.2 Collection Details

#### 12.2.1 users Collection
**Schema File**: server/models/User.js
**Purpose**: Store user account information and profiles
**Key Fields**:
- _id: MongoDB ObjectId (auto-generated)
- name: User's full name
- email: Unique email address
- password: Hashed password
- role: User role (user/admin)
- profile: Nested object with personal information
- createdAt, updatedAt: Timestamps

**Indexes**:
- email: Unique index for fast lookup
- createdAt: For sorting and analytics

#### 12.2.2 services Collection
**Schema File**: server/models/Service.js
**Purpose**: Store property listing information
**Key Fields**:
- _id: MongoDB ObjectId (auto-generated)
- title: Property title
- propertyType: Type of property
- location: Nested object with address details
- price: Monthly rent amount
- availability: Date range and status
- propertyDetails: Bedrooms, bathrooms, etc.
- amenities: Available facilities
- owner: Reference to users collection
- createdAt, updatedAt: Timestamps

**Indexes**:
- location.district: For location-based queries
- location.area: For area-specific searches
- price: For price range filtering
- owner: For owner's listings

#### 12.2.3 bookings Collection
**Schema File**: server/models/Booking.js
**Purpose**: Store booking requests and status
**Key Fields**:
- _id: MongoDB ObjectId (auto-generated)
- service: Reference to services collection
- user: Reference to users collection
- startDate, endDate: Booking period
- totalAmount: Total booking cost
- status: Booking status
- paymentStatus: Payment status
- confirmationCode: Unique booking code
- createdAt, updatedAt: Timestamps

**Indexes**:
- user: For user's booking history
- service: For property booking history
- startDate, endDate: For availability checking

#### 12.2.4 payments Collection
**Schema File**: server/models/Payment.js
**Purpose**: Store payment transaction records
**Key Fields**:
- _id: MongoDB ObjectId (auto-generated)
- booking: Reference to bookings collection
- user: Reference to users collection
- service: Reference to services collection
- amount: Payment amount
- paymentMethod: Method used for payment
- status: Payment status
- paymentDetails: Method-specific details
- createdAt, updatedAt: Timestamps

**Indexes**:
- user: For user's payment history
- booking: For booking-payment relationship
- status: For status-based queries
- createdAt: For chronological sorting
